# API Overview

The Stellar RWA API is a **read-only** REST service that indexes all tokenized
asset activity on Stellar and serves it as JSON. It is written in Rust (Axum +
tokio) and holds no keys — it never signs or submits transactions.

**Base URL:** Set via environment variable `NEXT_PUBLIC_API_BASE_URL` (defaults to `http://localhost:8080` for development). Readers should replace examples with their configured URL.

<CalloutBox variant="tip">
An OpenAPI 3.0 specification is available at <code>/openapi.json</code> — use it with Swagger UI, Postman, or to generate SDK clients. See <a href="/docs/integration">Integration Guide</a> for examples.
</CalloutBox>

## Non-goals

The API is deliberately limited. It does **not**:

- **Hold keys.** No secret key is configured or stored. The only account it
  knows about, `RWA_READ_SOURCE`, is a public address used as the unsigned
  source of simulated view calls.
- **Sign or submit transactions.** Every contract read is a
  `simulateTransaction` envelope with an empty signature set that is never
  sent to the network. Every route is a `GET`; there is no write endpoint.
- **Change on-chain state.** Issuing, transferring, allowlisting and dividend
  claims all happen through the web app, signed by the user's wallet (see
  [Integration Guide](/docs/integration)).
- **Act as the source of truth.** It is a ~10-second-old in-memory cache of
  the Soroban ledger, with no database.

**Trust implication:** compromising the API cannot move funds, change an
allowlist, or authorize anything on-chain — there is nothing to steal and no
signing path to abuse. The worst a faulty or malicious API can do is serve
stale or incorrect data, so verify anything security-critical against the
ledger directly before acting on it. See
[Architecture](/docs/architecture) for how this fits the wider system.

## How indexing works

A background task polls **Soroban RPC** every 10 seconds. On each tick it reads the
current state of the four contracts by *simulating* view calls — `get_all_assets`
on the registry, then per-asset `get_metadata`, `get_allowlist`, `balance` and
`get_distributions_for_asset` — and rebuilds an in-memory snapshot. For the full
polling model and what it means for data freshness, see
[How the indexer rebuilds state](/docs/architecture#how-the-indexer-rebuilds-state).

<CalloutBox variant="note">
State is kept **in memory** (no database in v1). If the RPC is briefly
unreachable, the indexer logs the error, keeps serving the last good snapshot, and
retries on the next tick. The API never panics on a transient failure.
</CalloutBox>

## Operational details

### Authentication and rate limiting

There is currently **no authentication** required to call the data endpoints
(everything under `/v1`, plus `/`, `/version` and `/health`). The one exception
is the operator-only [`/metrics`](#metrics-endpoint) endpoint, which requires a
bearer token.

The API applies request throttling, and its `/v1` data routes support HTTP
caching with `Cache-Control` and ETags. The `X-RateLimit-*` response headers
described in the reference are planned; caching is already available:

<CalloutBox variant="tip">
See <a href="/docs/api/rate-limits">Rate Limits &amp; Caching</a> for the
active ETag conditional-request flow and cache headers, along with the planned
rate-limit response headers and polling recommendations.
</CalloutBox>

### Data freshness and caching

The API refreshes its in-memory state approximately **every 10 seconds** by polling
Soroban RPC. This means:

- Data lags the ledger by ~10 seconds on average.
- Two requests made within the same 10-second window will return identical data.
- If Soroban RPC is temporarily unreachable, the API continues serving the last
  successful snapshot (no error, just stale data).

For integrations where you need real-time data, consider reading contracts directly
via Soroban RPC.

### Metrics endpoint

`GET /metrics` exposes indexer health in the
[Prometheus text exposition format](https://prometheus.io/docs/instrumenting/exposition_formats/)
(`Content-Type: text/plain; version=0.0.4`). It is intended for operators, not
API consumers, and is **not** part of the `/v1` namespace or its stability
promise.

#### Authentication

The endpoint is protected by a static bearer token configured on the server:

| Environment variable | Purpose |
|----------------------|---------|
| `RWA_METRICS_TOKEN` | Shared secret that scrapers must present. |

Scrapers send it in the `Authorization` header:

```bash
curl -H "Authorization: Bearer $RWA_METRICS_TOKEN" http://localhost:8080/metrics
```

- The header must be exactly `Bearer <token>`; the token is compared verbatim.
- A missing, malformed or wrong token returns `401 Unauthorized` with the plain
  text body `metrics authentication required`.
- If `RWA_METRICS_TOKEN` is **unset or empty**, the endpoint is disabled and
  every request returns `401`. There is no way to expose metrics without a token.
- The variable is read on every request, but since it comes from the process
  environment, rotating it means restarting the API with the new value.

<CalloutBox variant="warning">
Treat <code>RWA_METRICS_TOKEN</code> like any other secret: generate a long random
value (for example <code>openssl rand -hex 32</code>), keep it out of source control,
and serve the API over TLS so the token is not sent in clear text.
</CalloutBox>

#### Exposed metrics

| Metric | Type | Labels | Description |
|--------|------|--------|-------------|
| `rwa_indexer_refresh_duration_seconds` | summary | — | Wall-clock time of each indexer refresh (one sample per poll tick, successful or not). Rendered with `quantile` series plus `_sum` and `_count`. |
| `rwa_indexer_refresh_total` | counter | `outcome` = `success` \| `failure` | Number of completed refresh attempts. A failure means the whole tick failed and the previous snapshot kept being served. |
| `rwa_indexer_asset_read_errors_total` | counter | `asset_id`, `read` = `get_metadata` \| `compliance` \| `dividends` \| `dividend_decode` | Per-asset RPC reads that failed during an otherwise successful refresh. |

Series only appear after they are first recorded, so a freshly started API may
return an empty body until the first refresh completes, and
`rwa_indexer_asset_read_errors_total` is absent until a read actually fails.

Useful alert starting points:

```promql
# Refreshes are failing
rate(rwa_indexer_refresh_total{outcome="failure"}[5m]) > 0

# No successful refresh in the last minute (normal cadence is ~10s)
increase(rwa_indexer_refresh_total{outcome="success"}[1m]) == 0

# A specific asset keeps failing to read
increase(rwa_indexer_asset_read_errors_total[15m]) > 0
```

For snapshot age, use `GET /health`, which returns `503` with
`"status": "degraded"` once the snapshot is older than three poll intervals.

#### Example scrape configuration

Store the token in a file readable by Prometheus and reference it with
`credentials_file`, so it never appears in the config itself:

```yaml
scrape_configs:
  - job_name: stellar-rwa-api
    scrape_interval: 15s
    metrics_path: /metrics
    scheme: https
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/secrets/rwa-metrics-token
    static_configs:
      - targets: ["rwa-api.example.com"]
```

A scrape interval of 10–15 seconds matches the indexer's poll cadence; scraping
faster does not yield new data.

## Versioning and stability

All data endpoints are served under the `/v1` prefix (for example
`GET /v1/assets/:id`). The path prefix is the compatibility contract: a client
written against `/v1` should keep working, unmodified, for as long as `/v1` is
served. `GET /version` returns the running server version so clients can log or
report it, but clients should not need to branch on it.

### What `/v1` covers

The stability promise applies to every route under `/v1`, including its path and
query parameters, response JSON shapes, field types and meanings, HTTP status
codes, and the [error body](#error-responses) format and `error` codes.

It does **not** cover operator-facing routes (`/metrics`, `/health`, `/`), the
exact values of rate-limit budgets, the indexing interval, or anything marked as
experimental or planned in these docs.

### Changes that may ship without a version bump

These are **additive** or behavioural changes that a well-behaved client already
tolerates. Clients must ignore unknown fields and unknown enum values to benefit
from them.

- Adding new endpoints under `/v1`.
- Adding new **optional** query parameters with a default that preserves the
  current behaviour.
- Adding new fields to response objects.
- Adding new values to open-ended string enums (for example a new event type or
  a new `error` code for a previously unhandled case).
- Adding new response headers.
- Changing the wording of human-readable `message` strings.
- Changing ordering where the order is not documented as guaranteed.
- Tuning operational limits (rate limits, timeouts, body size, poll interval)
  and fixing bugs so behaviour matches the documentation.

### Changes that require a new version

These are **breaking** and will only ship under a new prefix (`/v2`):

- Removing or renaming an endpoint, field, or query parameter.
- Changing a field's type or encoding (for example turning a decimal string
  such as `total_supply` into a number) or its units (for example cents to
  dollars).
- Making an optional parameter required, or changing a default in a way that
  alters results.
- Changing the status code or `error` code returned for an existing condition.
- Changing the meaning of an existing field or the semantics of an endpoint.
- Changing pagination, ETag, or error-body structure.

### Deprecation policy

- When `/v2` is introduced, `/v1` keeps running alongside it; the two are
  served from the same process and index.
- A deprecation is announced in these docs and the changelog before anything is
  removed, and `/v1` remains available for **at least 6 months** after `/v2` is
  generally available.
- Individual `/v1` fields or endpoints may be marked deprecated in the docs and
  the OpenAPI spec (`deprecated: true`) ahead of time, but are not removed from
  `/v1` itself.
- Security fixes may change behaviour without notice when there is no
  compatible alternative; such changes will be called out in the changelog.

## Conventions

- **Large integers are strings.** Token amounts and valuations are `i128`
  on-chain. To avoid precision loss in JavaScript, they are serialized as decimal
  **strings** (`total_supply`, `valuation_cents`, `balance`, `total_amount`).
- **Convenience floats.** Valuations also include a `valuation_usd` (float
  dollars) and percentages (`share_percent`, `claimed_percent`) for display.
- **Amounts are raw base units.** Divide by `10 ** decimals` to get a display
  value. The asset's `decimals` is included on each asset.
- **Cents.** `valuation_cents` is USD cents; `valuation_usd = valuation_cents / 100`.

## Error responses

The response body depends on where an error is generated. Resource-not-found
errors use the API's JSON format:

```json
{
  "error": "not_found",
  "message": "no asset with id 999"
}
```

For this API-generated JSON body, `error` is a machine-readable code and `message`
is a human-readable explanation. Request-extraction failures and middleware errors
are generated by the HTTP framework and may instead return plain text. Branch on
the HTTP status; do not assume every failure uses the JSON shape above.

**Common errors:**

| HTTP status | Body format | Meaning |
|--------------|-------------|---------|
| `400 Bad Request` | Plain-text diagnostic | A path parameter or query value cannot be parsed, such as a non-numeric asset `:id` or malformed pagination value. |
| `401 Unauthorized` | Plain text | `/metrics` was called without a valid bearer token. |
| `404 Not Found` | JSON `{"error":"not_found","message":"..."}` for a missing resource | The requested asset or distribution does not exist. An unknown URL may use the framework's not-found response instead. |
| `429 Too Many Requests` | Plain-text throttle message | The per-IP rate limit was exceeded. See [Rate Limits & Caching](/docs/api/rate-limits) for the response and backoff guidance. |
| `500 Internal Server Error` | Not a stable API error shape | An unexpected server failure occurred. Treat the body as diagnostic and report persistent failures. |
| `503 Service Unavailable` | JSON health status | `GET /health` reports `degraded` when the indexed snapshot is too old. The body includes `snapshot_age_seconds` and `max_age_seconds`. |

Only the resource-not-found JSON body is a stable API error schema today. The
plain-text framework and middleware messages are useful for debugging, but clients
should not parse them to decide how to handle a failure.

## CORS

All origins, methods and headers are allowed, so the docs site and the web app
can call the API directly from the browser.

## `/stats` response

```json
{
  "total_assets": 1,
  "active_assets": 1,
  "tvl_cents": "500000000",
  "tvl_usd": 5000000.0,
  "total_holders": 1,
  "total_distributions": 0,
  "last_indexed_ledger": 3514152,
  "last_updated": "2026-07-09T08:43:12.101772791+00:00"
}
```

`total_holders` is the count of **distinct approved addresses** across all assets;
`last_indexed_ledger` is the ledger the most recent successful refresh read from.

**Response schema** (`Stats`):

| Field | Type | Unit | Nullable | Description |
|-------|------|------|----------|-------------|
| `total_assets` | integer | Assets | No | Total indexed assets |
| `active_assets` | integer | Assets | No | Indexed assets marked active |
| `tvl_cents` | string | USD cents | No | Exact TVL as a decimal string |
| `tvl_usd` | number | USD | No | TVL in dollars |
| `total_holders` | integer | Distinct addresses | No | Addresses with a positive token balance across assets |
| `total_distributions` | integer | Distributions | No | Total indexed dividend distributions |
| `last_indexed_ledger` | integer | Ledger sequence | No | Ledger read by the last successful full refresh |
| `last_updated` | string | RFC 3339 timestamp | Yes | JSON `null` before a successful refresh |
