# Architecture overview

The Stellar RWA Toolkit is built around four Soroban smart contracts. Everything
else — the REST API, the web app, and this documentation site — is tooling around
those contracts. Understanding what each contract does, and how they depend on one
another, is the fastest way to get oriented.

## The four contracts

### Asset token

The `asset-token` contract is a compliant fungible token that represents a
fractional share of a tokenised real-world asset. It follows the SEP-41 token
interface (the Stellar equivalent of ERC-20) and adds compliance gating on top:
every `transfer` and every `mint` checks the sender and recipient against the
compliance contract before moving any balance. The issuer deploys one
`asset-token` per RWA — each Manhattan Loft, invoice, or commodity parcel is its
own independent token instance. The contract stores the asset's name, symbol,
type, total supply, decimals, USD valuation, and the address of its paired
compliance contract. See the [Asset token reference](/docs/contracts/asset-token)
for the full method list and error codes.

### Compliance contract

The `compliance` contract is the on-chain gatekeeper. It maintains a KYC
allowlist — one record per Stellar address — that tracks each holder's approval
status (`Approved`, `Pending`, `Rejected`, or `Suspended`), jurisdiction (an ISO
country code), and approval expiry (expressed as a ledger sequence number). The
single function `is_allowed` is the gate the `asset-token` calls on every
transfer: it returns `true` only if the address is approved, not expired, and in a
jurisdiction that the issuer has not blocked. Because the `asset-token` depends only
on the `is_allowed` interface, the issuer can swap the underlying compliance
contract (via `set_compliance`) without redeploying the token — useful for migrating
to a stricter policy. Each `asset-token` is paired with exactly one compliance
contract at deployment time. See the [Compliance contract reference](/docs/contracts/compliance)
for the allowlist methods and the [Compliance Guide](/docs/compliance-guide) for
the full operational model.

### Registry contract

The `registry` contract is the platform-wide, on-chain index of every tokenised
asset. When an issuer deploys an `asset-token` and its paired `compliance`
contract, they register the token in the registry, which assigns a monotonically
increasing numeric id and records the issuer address, asset type, valuation, and
active status. The registry is a **singleton** — there is one per deployment, not
one per asset. It exposes query helpers (`get_all_assets`, `get_assets_by_type`,
`get_assets_by_issuer`) that the API's background indexer calls on every poll
cycle to discover the full set of assets without hard-coding any token addresses.
It also aggregates total value locked (TVL) across all active assets. See the
[Registry contract reference](/docs/contracts/registry).

### Dividend contract

The `dividend` contract handles proportional yield distribution to token holders.
An issuer calls `create_distribution`, which pulls a specified amount of a payment
token (for example USDC) into the contract's escrow and records the distribution.
Each holder then claims their share — `total_amount × balance / total_supply` —
directly from escrow by calling `claim`. Balances are read **at claim time** from
the `asset-token`, not at distribution creation time. Like the registry, the
dividend contract is a **singleton** across the platform: one instance manages
distributions for all assets. See the [Dividend contract reference](/docs/contracts/dividend).

## How the contracts relate

The four contracts form two groups:

- **Per-asset pair:** `asset-token` + `compliance`. They are deployed and
  initialised together. The `asset-token` holds the address of its compliance
  contract and calls `is_allowed` on every transfer. The two are tightly coupled,
  but the coupling is one-directional: the compliance contract is unaware of the
  token; it only answers `is_allowed` queries.

- **Platform singletons:** `registry` + `dividend`. Each is deployed once per
  platform. Assets are registered in the registry by their issuer. The dividend
  contract manages distributions for all assets identified by their `asset-token`
  address.

```
                    ┌───────────────────────────────────────────────────────────┐
                    │                  Stellar network                          │
                    │                                                           │
                    │  Per-asset pair (one instance per RWA):                  │
                    │                                                           │
                    │  ┌──────────────────┐   is_allowed(from)   ┌──────────┐  │
                    │  │  asset-token     │ ──────────────────▶  │compliance│  │
                    │  │  (SEP-41 token   │ ──────────────────▶  │(KYC      │  │
                    │  │   + compliance   │   is_allowed(to)     │ allowlist)│  │
                    │  │   gate)          │                      └──────────┘  │
                    │  └──────────────────┘                                    │
                    │         │  balance, total_supply                         │
                    │         ▼                                                 │
                    │  Platform singletons (one instance per deployment):       │
                    │                                                           │
                    │  ┌──────────────────┐   ┌──────────────────────────────┐ │
                    │  │  registry        │   │  dividend                    │ │
                    │  │  (asset index,   │   │  (yield escrow and           │ │
                    │  │   TVL)           │   │   proportional claims)       │ │
                    │  └──────────────────┘   └──────────────────────────────┘ │
                    └───────────────────────────────────────────────────────────┘
```

The cross-contract dependency flows like this at runtime:

1. On every `transfer` or `mint`, the `asset-token` calls `compliance.is_allowed`
   for each party. If either returns `false`, the transaction reverts immediately
   — no balance moves, no event is emitted.
2. When an issuer registers a new asset, they call `registry.register_asset` with
   the deployed `asset-token` address. The API discovers new assets by polling
   `registry.get_all_assets`.
3. When an issuer creates a distribution, they call
   `dividend.create_distribution(asset_token, ...)`. Holders later call
   `dividend.claim(distribution_id, holder)`, which reads the holder's current
   balance from the `asset-token` at that moment.

<CalloutBox variant="note">
The `registry` and `dividend` contracts never call `is_allowed`. Only the
`asset-token` enforces the compliance gate. Registering an asset in the registry
or creating a dividend distribution does not require the issuer to be KYC-approved
by the asset's compliance contract.
</CalloutBox>

## How data flows

**Writes (user → chain)**

1. A user opens the web app and connects Freighter.
2. The web app builds a Soroban transaction and asks Freighter to sign it.
3. The signed transaction is submitted to Soroban RPC and lands on the ledger.
4. The contract executes — for example, an `asset-token` transfer triggers
   cross-contract `is_allowed` checks in the `compliance` contract.

**Reads (chain → API → web app)**

1. The API's background indexer calls `simulateTransaction` on Soroban RPC every
   10 seconds, decoding the returned `ScVal` with `stellar-xdr`.
2. The decoded state is held in an in-memory snapshot (no database in v1).
3. The web app — and any other client — fetches that snapshot over REST. This is
   cheaper and simpler than every client simulating its own contract calls.

<CalloutBox variant="note">
The API is a **read-only cache**, not the source of truth. The Soroban ledger is.
If you need data fresher than ~10 seconds, simulate the relevant view call
directly with the Stellar JS SDK — see the [Integration Guide](/docs/integration#reading-contracts-directly).
</CalloutBox>

## How the indexer rebuilds state

The indexer does **not** replay contract events to derive state. On every cycle
it re-reads the *current* contract state through simulated view calls and builds
a brand-new snapshot from scratch.

**The polling model**

1. Every 10 seconds (`POLL_INTERVAL` in `api/src/indexer/mod.rs`) a background
   task starts a refresh cycle.
2. It calls `get_all_assets` on the `registry`, then for each asset reads
   `get_metadata` on the `asset-token`, the allowlist and balances via the
   `compliance` contract, and `get_distributions_for_asset` on the `dividend`
   contract.
3. The results are assembled into a new snapshot (assets, holders, compliance
   summaries, dividends and `/stats`) and swapped in atomically. Readers see
   either the old snapshot or the new one — never a half-built mix.
4. Individual reads retry transient RPC errors in place with short backoff. If
   the cycle still fails, the previous snapshot keeps being served and the next
   attempt waits one poll interval (or the RPC's `Retry-After`, if it sent one).

Because each cycle is a full re-read, there is no event cursor to fall behind and
no replay after a restart: a freshly started API is empty until its first
successful cycle, then fully current.

**Freshness implications**

- **Lag.** Snapshot data trails the ledger by up to one poll interval plus the
  time the cycle takes. `last_indexed_ledger` and `last_updated` on
  [`/stats`](/docs/api/overview) tell you which ledger and when.
- **Dividends lag more.** Distribution lists are cached per asset for 60 seconds
  inside the indexer, so a new or claimed distribution can take up to ~60 seconds
  to appear.
- **Partial staleness.** If a single asset's reads fail, that asset keeps its
  previous data and carries an `index_error`, while the rest of the snapshot
  updates normally. Treat an asset with `index_error` as possibly stale.
- **HTTP caching.** Snapshot-backed responses carry
  `Cache-Control: public, max-age=10` and an `ETag` derived from
  `last_indexed_ledger`, so polling faster than every 10 seconds only returns
  the same data (or a `304`). See [Rate Limits & Caching](/docs/api/rate-limits).
- **In-memory only.** Nothing is persisted; a restart discards the snapshot and
  the indexer rebuilds it on the next cycle.

## What the API does and does not do

| Does | Does not |
|---|---|
| Poll Soroban RPC and cache the result | Hold private keys |
| Serve plain JSON over REST | Sign or submit transactions |
| Decode XDR `ScVal` from contract view calls | Store data persistently (in-memory only) |
| Provide aggregated stats (TVL, holder counts) | Enforce any access control beyond rate limiting |

Because the API never holds keys or submits transactions, it has a minimal attack
surface. All write operations go through the web app → Freighter → Soroban RPC
path, where the user's wallet is the only key holder.

## Interface contracts

The three layers communicate through two stable interfaces:

- **Soroban contract ABI** — the method names and `ScVal` types exposed by the
  four contracts. The API's `indexer/mod.rs` and the web app's SDK calls both
  depend on this.
- **REST API schema** — the JSON shapes documented in the [API Reference](/docs/api/overview).
  The web app fetches from these endpoints; you can too.

Changes to either interface are versioned. The API currently has no URL
versioning (all paths are `/...`); a `v2` prefix will be added when breaking
changes are needed.
