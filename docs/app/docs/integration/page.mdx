# Integration Guide

Examples in this guide use Testnet endpoints, contract IDs, and passphrase.
For the corresponding Mainnet configuration—including provider RPC URL, new
contract IDs, and real XLM fee considerations—see
[Mainnet integration](/docs/getting-started#mainnet-integration).

Three ways to integrate with the platform, from easiest to most direct:

1. **Query the REST API** — indexed, JSON, no XDR.
2. **Read contracts via the JS SDK** — live simulation of view calls.
3. **Submit transactions** — sign with Freighter and invoke contract methods.

## End-to-end read workflow

The [REST API](/docs/api/overview) is the simplest integration surface. It is
read-only and returns plain JSON. Follow this path to discover an asset, read its
details, check an address against the asset's live compliance gate, and list its
distributions.

<CalloutBox variant="note">
Set <code>API_BASE_URL</code> to the API origin (for example,
<code>http://localhost:8080</code>); the versioned data routes use the
<code>/v1</code> prefix.
</CalloutBox>

```bash
# 1. Discover assets and choose a registry id from the response.
curl "$API_BASE_URL/v1/assets"

# 2. Read the chosen asset. Note its compliance_contract and id.
curl "$API_BASE_URL/v1/assets/1"
```

3. Check an address against that asset's **live on-chain** compliance gate. Use
the `compliance_contract` from the asset response and a valid simulation source
account; no signing or submission is needed:

```ts
import {
  Account, Address, BASE_FEE, Contract, Networks, TransactionBuilder,
  rpc, scValToNative,
} from "@stellar/stellar-sdk";

const server = new rpc.Server("https://soroban-testnet.stellar.org");
const complianceContract = "<compliance_contract from step 2>";
const investor = "<Stellar address to check>";
const source = new Account(
  "GAIQGTOBTTLLDJ4SWGGESM7UWJ2DI4K3ZNHUSHPDKJL2IE5FKY3BSRAA", "0",
);

const tx = new TransactionBuilder(source, {
  fee: BASE_FEE, networkPassphrase: Networks.TESTNET,
})
  .addOperation(new Contract(complianceContract).call(
    "is_allowed",
    new Address(investor).toScVal(),
  ))
  .setTimeout(30)
  .build();

const sim = await server.simulateTransaction(tx);
if (rpc.Api.isSimulationError(sim)) throw new Error(sim.error);
const allowed = scValToNative(sim.result!.retval) as boolean;
console.log({ investor, allowed });
```

```bash
# 4. List distributions for the same registry id.
curl "$API_BASE_URL/v1/assets/1/dividends"
```

The `/v1/compliance/:address` API route is an indexed view of an address's
current holdings, not a live compliance-contract check. Use `is_allowed` above
when deciding whether a transfer will pass the on-chain gate. The indexer refreshes
about every 10 seconds, so API data may lag current contract state.

### TypeScript client

```ts
const API = `${process.env.NEXT_PUBLIC_API_BASE_URL ?? "http://localhost:8080"}/v1`;

export interface Asset {
  id: number;
  token_contract: string;
  name: string;
  symbol: string;
  asset_type: string;
  valuation_cents: string;
  valuation_usd: number;
  decimals: number;
  total_supply: string;
  holders: number;
  active: boolean;
  paused: boolean;
  compliance_contract: string;
}

export async function getAssets(): Promise<Asset[]> {
  const res = await fetch(`${API}/assets`, { cache: "no-store" });
  if (!res.ok) throw new Error(`API ${res.status}`);
  return res.json();
}

// Amounts are strings (i128) — parse with BigInt and format by decimals.
export function displaySupply(a: Asset): string {
  const raw = BigInt(a.total_supply);
  const base = 10n ** BigInt(a.decimals);
  return (Number(raw) / Number(base)).toLocaleString();
}
```

<CalloutBox variant="tip">
Always parse `valuation_cents`, `total_supply`, `balance`, and `total_amount` with
<code>BigInt(...)</code> — they are decimal strings to preserve `i128` precision.
</CalloutBox>

## Reading contracts directly

To read live state without the API, simulate a view call with the Stellar JS SDK.
No signing is required for reads.

```ts
import {
  Contract, TransactionBuilder, Account, BASE_FEE,
  Networks, rpc, scValToNative,
} from "@stellar/stellar-sdk";

const server = new rpc.Server("https://soroban-testnet.stellar.org");
const REGISTRY = "CBX5SMLTXX6JP4HA5GQIO2V6QM7WCUGL2GZ6D4U773HMRI6RXISKPUR3";

export async function totalValueLocked(): Promise<bigint> {
  const contract = new Contract(REGISTRY);
  // Any valid account works as the simulation source.
  const source = new Account(
    "GAIQGTOBTTLLDJ4SWGGESM7UWJ2DI4K3ZNHUSHPDKJL2IE5FKY3BSRAA", "0",
  );
  const tx = new TransactionBuilder(source, {
    fee: BASE_FEE, networkPassphrase: Networks.TESTNET,
  })
    .addOperation(contract.call("total_value_locked"))
    .setTimeout(30)
    .build();

  const sim = await server.simulateTransaction(tx);
  if (rpc.Api.isSimulationError(sim)) throw new Error(sim.error);
  return scValToNative(sim.result!.retval) as bigint; // USD cents
}
```

Check an address's compliance status the same way:

```ts
import { Address, nativeToScVal } from "@stellar/stellar-sdk";

const COMPLIANCE = "CBUERYDM7DXTZLLKDBRJKUBPFJ7M4OSUN4T7XKUARU345RLXNAIQD2IU";

const op = new Contract(COMPLIANCE).call(
  "is_allowed",
  new Address(investor).toScVal(),
);
// build → simulate → scValToNative(retval) === boolean
```

## Submitting transactions

Writes must be signed by the account that authorizes them. In the browser, sign
with Freighter:

```ts
import {
  Contract, TransactionBuilder, Networks, BASE_FEE, rpc, Address, nativeToScVal,
} from "@stellar/stellar-sdk";
import { signTransaction } from "@stellar/freighter-api";

const server = new rpc.Server("https://soroban-testnet.stellar.org");

export async function transfer(
  token: string, from: string, to: string, amount: bigint,
): Promise<string> {
  const account = await server.getAccount(from);
  const op = new Contract(token).call(
    "transfer",
    new Address(from).toScVal(),
    new Address(to).toScVal(),
    nativeToScVal(amount, { type: "i128" }),
  );
  const built = new TransactionBuilder(account, {
    fee: BASE_FEE, networkPassphrase: Networks.TESTNET,
  }).addOperation(op).setTimeout(60).build();

  // Simulate + assemble to attach the Soroban footprint and resource fees.
  const sim = await server.simulateTransaction(built);
  if (rpc.Api.isSimulationError(sim)) throw new Error(sim.error);
  const prepared = rpc.assembleTransaction(built, sim).build();

  const { signedTxXdr } = await signTransaction(prepared.toXDR(), {
    networkPassphrase: Networks.TESTNET, address: from,
  });
  const signed = TransactionBuilder.fromXDR(signedTxXdr, Networks.TESTNET);
  const sent = await server.sendTransaction(signed);
  return sent.hash; // then poll server.getTransaction(hash)
}
```

<CalloutBox variant="compliance">
A `transfer` will revert with <code>SenderNotCompliant (7)</code> or
<code>RecipientNotCompliant (8)</code> if either party is not KYC-approved. Check
<code>is_allowed</code> for both addresses before submitting to give users a clear
error up front.
</CalloutBox>

## The write path, stage by stage

The API is read-only, so every write goes wallet → Soroban RPC → contract. A
write always runs through the same six stages, in this order. Each stage fails
in its own way, and knowing which stage failed tells you what to do next.

| # | Stage | What happens | Failure modes | What to do |
|---|-------|--------------|---------------|------------|
| 1 | **Build** | Load the source account with `server.getAccount(from)` and build a transaction with one `contract.call(...)` operation. | Account not found (unfunded on this network); wrong contract id; argument that cannot be encoded as the expected `ScVal` (e.g. an `i128` passed as a JS `number`). | Fund the account, check the id against the registry's `get_all_assets`, encode amounts with `nativeToScVal(x, { type: "i128" })`. |
| 2 | **Simulate** | `server.simulateTransaction(built)` runs the call against current ledger state without submitting it. | `rpc.Api.isSimulationError(sim)` — the contract would revert (e.g. `SenderNotCompliant (7)`, `InsufficientBalance (4)`, `Paused (6)`, `Unauthorized (3)`), or the RPC is unreachable / rate limited. | Map the contract error code to a message (see the contract reference pages); nothing was signed or spent, so fix the input and retry. |
| 3 | **Assemble** | `rpc.assembleTransaction(built, sim).build()` attaches the footprint, auth entries, and resource fee from the simulation. | Simulation was a restore result (`rpc.Api.isSimulationRestore(sim)`) because contract state has been archived; assembling a stale simulation. | Submit the restore first, then re-simulate. Always assemble from the simulation of the exact transaction you built. |
| 4 | **Sign** | Freighter's `signTransaction(xdr, { networkPassphrase, address })` returns `signedTxXdr`. | User rejects the prompt (returns an `error`); Freighter is on a different network than `networkPassphrase`; the connected address is not the one that must authorize. | Treat rejection as a cancel, not an error; check the network and address before building. |
| 5 | **Submit** | `server.sendTransaction(signed)` hands the envelope to Soroban RPC. | `status` of `ERROR` (malformed or rejected, e.g. `txBadSeq`, `txInsufficientFee`), `TRY_AGAIN_LATER` (node busy), or `DUPLICATE`. | On `ERROR` read `errorResult`; on `TRY_AGAIN_LATER` resubmit the same signed envelope; on bad sequence rebuild from stage 1. |
| 6 | **Poll** | Call `server.getTransaction(hash)` until the status leaves `NOT_FOUND`. | `FAILED` — the contract reverted on-chain (state changed between simulate and apply, e.g. the holder was suspended); still `NOT_FOUND` after the transaction's timeout — it expired and will never land. | On `FAILED`, re-simulate to see the current error; on expiry rebuild from stage 1. |

Once the transaction is `SUCCESS`, the change is on the ledger immediately, but
the [REST API](/docs/api/overview) only reflects it after the indexer's next
refresh (about 10 seconds — see [How data flows](/docs/architecture#how-data-flows)).
Read the contract directly if you need to confirm the new state sooner.

### Worked example: transfer and wait for confirmation

This extends the `transfer` sample above with explicit handling for each stage.

```ts
import {
  Contract, TransactionBuilder, Networks, BASE_FEE, rpc, Address, nativeToScVal,
} from "@stellar/stellar-sdk";
import { signTransaction } from "@stellar/freighter-api";

const server = new rpc.Server("https://soroban-testnet.stellar.org");
const PASSPHRASE = Networks.TESTNET;

export async function transferAndConfirm(
  token: string, from: string, to: string, amount: bigint,
): Promise<string> {
  // 1. Build
  const account = await server.getAccount(from); // throws if unfunded
  const built = new TransactionBuilder(account, {
    fee: BASE_FEE, networkPassphrase: PASSPHRASE,
  })
    .addOperation(new Contract(token).call(
      "transfer",
      new Address(from).toScVal(),
      new Address(to).toScVal(),
      nativeToScVal(amount, { type: "i128" }),
    ))
    .setTimeout(60)
    .build();

  // 2. Simulate
  const sim = await server.simulateTransaction(built);
  if (rpc.Api.isSimulationError(sim)) {
    throw new Error(`simulation failed: ${sim.error}`); // e.g. Error(Contract, #7)
  }
  if (rpc.Api.isSimulationRestore(sim)) {
    throw new Error("contract state is archived; submit a restore first");
  }

  // 3. Assemble
  const prepared = rpc.assembleTransaction(built, sim).build();

  // 4. Sign
  const signedResult = await signTransaction(prepared.toXDR(), {
    networkPassphrase: PASSPHRASE, address: from,
  });
  if (signedResult.error) throw new Error("signature rejected");
  const signed = TransactionBuilder.fromXDR(signedResult.signedTxXdr, PASSPHRASE);

  // 5. Submit
  const sent = await server.sendTransaction(signed);
  if (sent.status === "ERROR") {
    throw new Error(`submit rejected: ${sent.errorResult?.result().switch().name}`);
  }
  if (sent.status === "TRY_AGAIN_LATER") {
    throw new Error("RPC busy; resubmit the same signed transaction");
  }

  // 6. Poll
  for (let i = 0; i < 30; i++) {
    const res = await server.getTransaction(sent.hash);
    if (res.status === rpc.Api.GetTransactionStatus.SUCCESS) return sent.hash;
    if (res.status === rpc.Api.GetTransactionStatus.FAILED) {
      throw new Error(`transaction ${sent.hash} failed on-chain`);
    }
    await new Promise((r) => setTimeout(r, 2000)); // NOT_FOUND: not yet in a ledger
  }
  throw new Error(`transaction ${sent.hash} not confirmed before timeout`);
}
```

The web app follows the same sequence; its progress indicator (*preparing →
awaiting signature → submitting → confirming*) maps to stages 1–3, 4, 5, and 6.
See [Transaction feedback](/docs/web-app#transaction-feedback).

## Retries, failover and rate limits

Public Soroban RPC endpoints are shared infrastructure: expect occasional
network errors, `503`s and `429`s. The reference API's indexer
(`api/src/indexer/mod.rs`) handles this as described below; a client that calls
RPC directly (as in the sections above) should follow the same pattern.

### Retry guidance

What the reference indexer does for each `simulateTransaction` read:

| Setting | Value |
| --- | --- |
| Attempts per read (first try + retries) | 4 (`MAX_READ_ATTEMPTS`) |
| Base delay | 150 ms, doubling per attempt |
| Maximum delay | 2 s |
| Jitter | Full jitter: a random delay in `[0, cap]` |

- **Retried in place:** only transport errors (connection failures, dropped or unreadable responses)
  and JSON-RPC or simulation errors returned in a `2xx` response.
- **Not retried:** XDR, strkey and JSON decode errors. These come from how the
  request was built or the response was parsed, so they fail the same way on
  every attempt. Other non-`2xx` HTTP statuses (for example `502`) are not
  retried in place either; the read fails and the refresh is retried on the
  next cycle.
- **Failed refresh:** if a read still fails, the whole refresh is abandoned,
  the API keeps serving the last good snapshot, and the indexer tries again
  after the 10 s poll interval.

For your own client: retry only idempotent calls (`simulateTransaction`,
`getLedgerEntries`, `getTransaction`), use capped exponential backoff with full
jitter so clients don't retry in lockstep, and keep the retry budget well under
your polling interval. Do not blindly re-send a `sendTransaction` after a
timeout. Poll `getTransaction` with the hash first, because the transaction may
already have been accepted.

### Failover

The reference API does **not** fail over between RPC endpoints. It reads a
single `RWA_RPC_URL` (default `https://soroban-testnet.stellar.org`). If that
endpoint is down, the indexer keeps serving the last good snapshot and
`last_indexed_ledger` in `GET /v1/stats` stops advancing. Watch that value, or the
`rwa_indexer_refresh_total{outcome="failure"}` metric, to detect an outage. To
switch providers, change `RWA_RPC_URL` and restart. A non-testnet URL also
requires `RWA_REGISTRY_ID` and `RWA_DIVIDEND_ID`.

If your own client needs failover, keep an ordered list of RPC URLs for the
**same network**. Move to the next URL only after its retry budget runs out,
not on the first error. Compare `latestLedger` across providers so you don't
read from a node that is lagging behind.

### Rate-limit interaction

- A `429 Too Many Requests` or `503 Service Unavailable` from RPC is **not**
  retried in place. Fast retries would only add load to a node that is already
  pushing back. The read fails, the refresh cycle ends, and the next cycle
  waits for the `Retry-After` header (integer seconds). If that header is
  missing or not an integer, it waits the normal 10 s poll interval instead.
- Retries count against the provider's rate limit. With 4 attempts per read, a
  single refresh can make up to 4× the normal number of requests during an
  incident. Size your request rate with that in mind.
- The REST API applies its own per-IP token-bucket limit to *your* client
  (`RWA_RATE_LIMIT_PER_SECOND` / `RWA_RATE_LIMIT_BURST`). Handle its `429`
  the same way and honour `Retry-After`. See
  [Rate Limits & Caching](/docs/api/rate-limits).
